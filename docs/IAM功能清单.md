# IAM功能清单

本文档基于当前仓库中的设计文档与实际代码实现进行整理，目标是回答两个问题：

1. 现在已经支持了哪些 IAM 能力；
2. 如果要把它建设成一个专业的集中式授权验证中心，还缺少哪些关键能力。

为便于判断优先级，文中使用以下状态：

- **已支持**：代码中已有可运行实现
- **部分支持**：已有基础实现，但产品体验、完整链路或安全深度不足
- **建议补充**：当前尚缺失，建议规划建设

## 一、当前已具备的功能

| 功能 | 状态 | 说明 |

## 二、从产品与技术角度看，当前还缺什么

下面分为 **必要** 与 **推荐** 两类。

### A. 必要补充清单

这些能力对于“集中式授权验证中心”来说，属于优先级很高、应尽快补齐的内容。

| 项目 | 为什么是必要的 |
| --- | --- |
| **1. 刷新令牌轮换与复用检测** | 当前刷新令牌流程会继续签发新令牌，但没有看到对旧刷新令牌做强制轮换/复用检测的完整安全策略。集中式认证中心必须防止 refresh token 被窃取后长期滥用。 |
| **2. 后台与 OAuth 会话模型统一** | 当前管理后台登录走的是自定义 `api/admin/login` + 本地 token 存储，OAuth 授权页/登录页又走 Cookie + Razor Pages，两套登录形态并存，不利于统一 SSO、会话注销与安全策略。 |
| **3. 完整的用户自助认证闭环** | 忘记密码、重置密码、邮箱/手机号验证、注册审核等仍未形成闭环。没有这些能力，系统更像“管理员工具”，而不是完整身份中心。 |
| **4. MFA 真正落地** | 实体中已有 `IsTwoFactorEnabled` 字段，但没有看到 TOTP、短信/邮件 OTP、恢复码、设备记忆、Step-up Authentication 等完整实现。对集中式认证中心来说，这是基础安全能力。 |
| **5. 外部身份源联邦登录闭环** | 目前外部登录控制器拿到 Google/Microsoft 用户信息后仍停留在 TODO，缺少账号绑定、首次建档、冲突处理、回填 claims、联邦注销等关键逻辑。 |
| **6. 客户端认证与敏感端点保护加固** | 自省、撤销等端点当前未体现严格的客户端认证/授权策略；对于集中式认证中心，这些端点必须防止任意客户端滥用。 |
| **7. 后台权限模型真正生效** | `HasPermissionAsync` 在多个 Manager 中仍是 deny-by-default 的占位实现，说明权限模型尚未真正完备。要让管理后台可用于生产，必须把操作级权限策略落地。 |
| **8. 设备码与授权交互闭环** | 后端已有设备授权入口和授权页基础，但设备码用户确认、授权确认、异常处理、授权拒绝反馈等前后端交互链路仍不完整。对于集中式认证中心，这些用户交互必须形成可用闭环。 |
| **9. 生产级 CORS / Issuer / Secret 管理** | 目前模块默认 CORS 是 `AllowAnyOrigin`，Discovery 还可能 fallback 到请求地址；同时本地配置依赖外部连接串。生产级认证中心必须严格收敛跨域、显式配置 Issuer，并把敏感配置迁移到安全存储。 |
| **10. 统一注销与会话传播** | 当前有本地注销与会话记录，但还缺少前后端协同注销、跨客户端 SSO 会话一致性、联邦退出等机制。没有它，集中式登录中心的体验会断裂。 |

### B. 推荐补充清单

这些能力不是“今天不做系统就不能跑”，但如果目标是专业级、可推广的 IAM 平台，建议纳入中期规划。

| 项目 | 推荐原因 |
| --- | --- |
| **1. Passkey / WebAuthn** | 可显著提升安全性与登录体验，是现代身份平台的重要方向。 |
| **2. 风险控制与防滥用能力** | 包括限流、验证码、IP/设备指纹、异常登录检测、地理位置告警等，可提升认证中心抗攻击能力。 |
| **3. 动态客户端注册 / 开发者门户** | 方便内部平台化推广，减少人工创建客户端的运维成本。 |
| **4. SCIM / HR / 企业组织同步** | 如果系统将面向多系统统一身份治理，组织与账号同步能力会很重要。 |
| **5. 多租户隔离能力** | 当前 `AppHost` 配置里虽然有多租户开关语义，但整体产品层面尚未体现租户隔离的完整模型。若面向集团/多部门/多业务线，此能力价值很高。 |
| **6. 高级 OAuth 安全规范支持** | 如 PAR、JAR/JARM、DPoP、Token Exchange、RAR、FAPI 等，可提升对高安全场景和外部生态的适配性。 |
| **7. 审计报表与导出分析** | 当前审计更偏查询，若要支持安全合规、内控与运营，需要报表、导出与检索能力。 |
| **8. 运营后台与告警面板** | 包括签名密钥即将过期提醒、客户端密钥过期提醒、异常流量告警、令牌签发统计等。 |
| **9. 身份资料与 Claims 映射治理** | 集中式认证中心通常需要更细粒度的 claims 策略、映射模板、最小化披露与不同客户端差异化下发。 |
| **10. 废弃密码模式（ROPC）或限制其使用范围** | 当前 Token 端点仍支持 Password Grant。对于现代 OAuth 平台，建议尽量减少或限制该模式，仅用于极少数受控场景。 |

## 三、对当前项目阶段的判断

如果从成熟度来评价，当前项目更接近：

> **“具备 OAuth/OIDC 核心能力的 IAM 平台基础版 / 原型版”**

而距离一个可稳定承载多个业务系统的“专业集中式授权验证中心”，还需要继续补齐：

- 用户自助闭环
- 强认证与联邦认证闭环
- 管理权限体系落地
- 生产级安全加固
- 运维治理与一致性打磨

## 四、建议的建设顺序

为了兼顾产品价值与工程落地，建议优先按以下顺序建设：

1. **统一登录与会话模型**（管理后台 / OAuth / SSO）
2. **补齐用户自助认证闭环**（注册验证、找回密码、重置密码）
3. **上线 MFA**（先 TOTP，再扩展 WebAuthn）
4. **补齐外部身份联邦登录闭环**
5. **加固 Token / Client / CORS / Issuer / Secret 安全策略**
6. **补齐设备码与授权交互闭环**
7. **再做平台化增强**（多租户、动态客户端注册、SCIM、运营面板等）

## 五、结论

这个仓库已经不是“从零开始”，因为它已经具备：

- 标准协议端点
- 基础数据模型
- 管理后台框架
- 示例项目与本地编排能力

但如果目标是成为真正的企业级集中认证中心，**下一阶段工作的重点已经不是“有没有端点”，而是“是否形成完整产品闭环与生产级安全治理能力”**。
