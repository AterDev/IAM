# Stage1：前端功能开发任务

## 目标

本阶段聚焦 `IAM功能清单` 中“必要补充清单”的前端部分，目标是让当前管理后台与认证相关页面从“基础演示可见”提升到“可指导后续连续开发和编码落地”。

本文档面向后续编码型 LLM 或工程师，强调：

- 以现有 Angular 管理端结构为基础
- 不编造后端尚不存在的功能
- 前端改造要围绕真实认证中心场景，而不是只做页面摆设

## 范围边界

本阶段前端优先处理以下事项：

1. 为统一会话模型做前端适配准备
2. 补齐注册、找回密码、重置密码等自助流程页面
3. 补齐 MFA 交互流程
4. 补齐外部身份登录入口与回调承接
5. 完善授权确认与设备码确认页面
6. 强化后台权限感知与错误反馈
7. 完善统一注销体验

## 任务执行方式

为便于直接交给 LLM 继续编码，下面每个任务都补充为可执行任务卡片，重点看四个维度：

- **先后依赖**：先做什么、后做什么，避免 UI 与接口脱节
- **建议拆分**：建议分步骤推进，降低单次改动复杂度
- **预计改动文件**：优先锁定高概率改动文件
- **测试点**：至少具备可手工验证的最小闭环

## 任务 1：为统一会话模型做前端适配准备

- 目标：

当前 `WebApp` 的管理员登录依赖本地 `accessToken + localStorage` 状态。Stage1 需要先把前端结构调整到便于后续切换统一认证模型。

- 重点文件：

- `src/ClientApp/WebApp/src/app/services/auth.service.ts`
- `src/ClientApp/WebApp/src/app/pages/login/login.ts`
- 路由守卫与请求拦截相关代码

- 实现要点：

- 抽象认证状态，而不是把 token 存取逻辑散落页面组件
- 区分：
  - 当前用户信息
  - 是否已登录
  - 会话是否过期
  - 是否需要二次验证
- 为后续切换到 OIDC / cookie session / silent renew 预留接口层

- 注意事项：

- Stage1 不要求一次引入完整 OIDC 客户端到管理端
- 但要避免继续加重 `localStorage + 手写状态` 的耦合

- 先后依赖：

- 建议作为前端 Stage1 的第 1 个任务优先处理
- 与后端 Stage1 任务 2（统一会话模型）需同步约定字段与状态语义

- 建议拆分：

1. 抽象认证状态服务
2. 整理路由守卫与请求拦截
3. 替换页面中的散落登录状态判断

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/services/auth.service.ts`
- `src/ClientApp/WebApp/src/app/share/auth.guard*`
- `src/ClientApp/WebApp/src/app/pages/login/*`

- 测试点：

- 已登录用户刷新页面后状态一致
- 未登录用户访问受保护路由会被正确拦截
- 过期/失效状态可被统一识别

## 任务 2：补齐注册、找回密码、重置密码流程页面

- 目标：

让当前已有页面从“只有表单”变成“能和真实后端接口配合”的完整用户流。

- 重点页面：

- `register`
- `forgot-password`
- `login`

- 实现要点：

- 注册页：
  - 成功提示
  - 失败原因展示
  - 验证状态说明（如需邮箱验证）
- 找回密码页：
  - 申请验证码/重置链接
  - 提交重置参数
  - 过期、失效、重复使用等异常提示

- 注意事项：

- 不要继续保留“setTimeout 模拟成功”逻辑
- 文案要准确区分：账号不存在、链接失效、密码不符合规则等场景

- 先后依赖：

- 依赖后端 Stage1 任务 3 提供真实接口
- 建议在任务 1 完成认证服务抽象后推进

- 建议拆分：

1. 去除模拟逻辑
2. 接入真实注册 / 找回密码 / 重置密码接口
3. 补成功、失败、过期等页面状态

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/pages/register/*`
- `src/ClientApp/WebApp/src/app/pages/forgot-password/*`
- `src/ClientApp/WebApp/src/app/services/api/**`

- 测试点：

- 注册成功 / 重复账号 / 验证失败
- 找回密码申请成功 / 重置链接过期 / 验证码错误
- 重置成功后可使用新密码登录

## 任务 3：补齐 MFA 前端交互

- 目标：

让 MFA 不只是一个用户属性字段，而是前端可操作、可验证的流程。

- 建议交付：

- 用户安全设置中增加 MFA 开启/关闭页面
- 首次绑定 TOTP 的二维码/密钥展示页
- 登录后 MFA 验证页
- 恢复码展示与下载提示

- 注意事项：

- 二维码、共享密钥、恢复码属于敏感信息，展示时要遵循一次性原则
- MFA 验证失败、次数限制、恢复码已用尽等状态要有清晰提示

- 先后依赖：

- 依赖后端 Stage1 任务 4
- 最好在登录状态抽象完成后再接入 MFA 中间态

- 建议拆分：

1. 增加安全设置中的 MFA 管理入口
2. 接入绑定 / 校验 / 关闭流程
3. 接入登录后的 MFA 二次验证页面

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/pages/**`
- `src/ClientApp/WebApp/src/app/services/**`
- 可能新增 `security/mfa` 相关页面目录

- 测试点：

- 开启 MFA 后登录进入二次验证步骤
- 错误验证码被正确拦截
- 恢复码只允许成功使用一次

## 任务 4：补齐外部身份登录入口与回调承接

- 目标：

为 Google / Microsoft 等外部身份源登录提供可用的前端入口与跳转承接。

- 实现要点：

- 登录页增加外部登录入口按钮
- 明确回调后页面跳转策略
- 对首次绑定、账号冲突、需要补充资料等状态提供 UI 承接

- 注意事项：

- 不要假设外部登录一定成功
- 要能展示“账号未绑定”“邮箱冲突”“需要管理员审核”等后端返回状态

- 先后依赖：

- 依赖后端 Stage1 任务 5
- 与登录页改造、统一会话模型适配有关

- 建议拆分：

1. 增加外部登录按钮与跳转逻辑
2. 增加回调承接与状态分流页面
3. 增加绑定/冲突提示 UI

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/pages/login/*`
- `src/ClientApp/WebApp/src/app/app.routes.ts`
- 可新增 `external-auth` 承接页面

- 测试点：

- 外部登录成功后回到正确页面
- 账号未绑定 / 邮箱冲突有明确提示
- 用户取消外部登录时流程可恢复

## 任务 5：完善授权确认与设备码确认页面

- 目标：

让授权页与设备码页真正成为认证中心的用户交互页面，而不是静态演示页面。

- 重点页面：

- `authorize`
- `device-code`

- 当前问题：

- `authorize` 仍有模拟回调逻辑
- `device-code` 仍是 TODO / 模拟流程

- 实现要点：

- 授权页：
  - 从真实接口读取客户端信息、作用域信息、授权状态
  - 支持同意 / 拒绝
  - 正确处理跳转与错误反馈
- 设备码页：
  - 输入 user code
  - 调用真实确认接口
  - 展示成功、拒绝、过期、无效码等状态

- 注意事项：

- 不要在前端拼装“假的 code 回调”
- 用户看到的客户端名称、作用域描述应尽量来自后端真实数据

- 先后依赖：

- 依赖后端 Stage1 任务 8
- 建议在任务 2 完成后推进，避免继续保留模拟交互

- 建议拆分：

1. 用真实接口替代模拟 authorize / device code 逻辑
2. 补充同意、拒绝、过期、无效码等状态处理
3. 打磨客户端信息与 scope 展示

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/pages/authorize/*`
- `src/ClientApp/WebApp/src/app/pages/device-code/*`
- `src/ClientApp/WebApp/src/app/services/api/**`

- 测试点：

- 授权同意 / 拒绝跳转正确
- 设备码有效 / 无效 / 过期展示正确
- 不再存在本地拼装假的授权码逻辑

## 任务 6：强化后台权限感知与错误反馈

- 目标：

在服务端权限落地后，前端也需要同步补齐权限感知与受限场景处理。

- 实现要点：

- 菜单、按钮、页面入口按权限展示
- 对 401 / 403 / 业务权限不足做统一处理
- 对敏感操作给出明确提示，不使用模糊错误文案

- 注意事项：

- 前端权限控制只用于体验增强，不可替代服务端鉴权
- 要避免“页面能点开，提交后才发现无权限”的糟糕体验

- 先后依赖：

- 依赖后端 Stage1 任务 7 提供明确权限语义
- 建议在核心页面接口稳定后统一处理

- 建议拆分：

1. 统一 401 / 403 / 业务权限不足错误处理
2. 增加菜单、按钮、页面级权限感知
3. 增加无权限提示与跳转处理

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/layout/**`
- `src/ClientApp/WebApp/src/app/share/**`
- 各管理页面列表与详情组件

- 测试点：

- 无权限用户看不到或无法进入敏感页面
- 有权限用户不受影响
- 401 / 403 状态反馈清晰一致

---

## 任务 7：完善统一注销体验

- 目标：

让管理后台与认证中心的退出行为一致、可理解。

- 实现要点：

- 退出时清理本地状态
- 调用统一注销接口
- 正确处理注销后的跳转
- 对“会话已失效”“远程撤销后被踢下线”给出提示

- 注意事项：

- 不要只清本地缓存就算退出完成
- 要考虑 token 过期、会话撤销、前后端状态不同步等场景

- 先后依赖：

- 依赖后端 Stage1 任务 10
- 与任务 1 的认证状态抽象直接相关

- 建议拆分：

1. 统一前端退出入口与本地状态清理
2. 调用统一注销接口
3. 增加被动登出 / 会话失效提示

- 预计改动文件：

- `src/ClientApp/WebApp/src/app/services/auth.service.ts`
- `src/ClientApp/WebApp/src/app/layout/**`
- 全局拦截器与路由守卫

- 测试点：

- 主动退出后本地状态清空且页面跳转正确
- 后端撤销会话后前端能感知并提示
- 不会出现“页面显示已退出但接口仍可调用”的状态错乱

## 页面与模块优先级建议

建议按以下顺序推进前端开发：

1. 登录状态与认证服务抽象
2. 找回密码 / 重置密码
3. 授权确认页与设备码页
4. MFA 页面
5. 外部登录入口与回调承接
6. 权限感知与统一注销体验

## 交付要求

本阶段前端完成后，应至少满足：

- 不再保留核心认证流程中的“模拟成功”逻辑
- 页面状态与后端真实认证状态一致
- 所有关键错误场景有明确文案
- 认证相关页面可以被后续 LLM 直接理解并继续编码

## 测试建议

- 登录成功 / 失败
- 找回密码成功 / 链接失效 / 验证码错误
- 授权同意 / 拒绝
- 设备码有效 / 无效 / 过期
- MFA 正确验证码 / 错误验证码 / 恢复码
- 外部登录成功 / 未绑定 / 冲突
- 会话失效后的页面回退与重新登录
